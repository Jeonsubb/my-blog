1. 한눈에 보기

이 블로그는 Next.js 16 App Router 단일 애플리케이션입니다. 화면 렌더링과 API가 하나의 프로젝트 안에 함께 있고, Vercel에 서버리스 형태로 배포됩니다. 별도의 백엔드 서버는 없으며, 데이터는 전부 Supabase(PostgreSQL)에 저장됩니다.

약 4,900줄TS/TSX/MJS/SQL/CSS 합계
5개API 라우트 (app/api/**/route.ts)
3개 테이블posts · comments · traffic_logs
3개 외부 서비스Supabase · Google Gemini · GitHub API
영역기술비고
프레임워크Next.js 16.2 (App Router), React 19.2, TypeScript서버 컴포넌트 중심 구조입니다.

관측@vercel/analytics, 자체 traffic_logs 테이블Grafana, Sentry 같은 APM은 없습니다.

2. 전체 아키텍처 설계도

요청은 브라우저에서 출발해 Vercel의 미들웨어를 먼저 통과하고, 그다음 페이지(서버 컴포넌트) 또는 API 라우트로 전달됩니다. 페이지와 API는 모두 lib/ 계층을 거쳐 외부 서비스에 접근합니다.

클라이언트 컴포넌트 ("use client") 미들웨어 서버 컴포넌트 · Route Handler 도메인 로직 (lib/) 외부 서비스 점선 화살표는 응답과 무관하게 백그라운드에서 실행되는 호출입니다.

5. 흐름 ② 관리자 인증과 글쓰기

6. 흐름 ③ 익명 댓글

댓글은 로그인 없이 닉네임과 비밀번호만으로 작성합니다. 수정이나 삭제를 요청하면 서버가 저장된 해시와 입력값을 비교해 본인인지 확인합니다. 조회(GET)만 anon 키를 쓰고, 작성·수정·삭제와 비밀번호 해시 조회는 service-role 키로 처리합니다. anon 키의 쓰기 권한과 password 컬럼 조회 권한은 scripts/sql/comments-rls.sql로 회수합니다.

12. 현재 구조의 약점과 개선 방향

심각도내용근거개선 방향
해결 댓글 API가 anon 키로 비밀번호 조회·수정·삭제를 수행해서, 누구든 브라우저에 노출된 anon 키로 Supabase REST를 직접 호출하면 비밀번호 검증 없이 댓글을 지우거나 해시를 읽을 수 있었습니다. 커밋 e0aa223 쓰기와 비밀번호 조회를 getSupabaseAdminClient()로 옮겼습니다. Supabase에서 scripts/sql/comments-rls.sql을 실행해야 anon 권한 회수까지 완료됩니다.
중간 공개 AI API가 인증과 호출 제한 없이 임의의 content를 Gemini로 전달합니다. 외부에서 무료 LLM 프록시처럼 악용할 수 있습니다. app/api/ai/post/route.ts:26-46 slug만 받아 서버에서 본문을 조회하고, 결과를 글 단위로 캐시하며, Redis(Upstash)로 IP별 호출 횟수를 제한합니다.
중간 CLI로 게시하면 캐시 무효화가 일어나지 않습니다. scripts/publish-study-post.mjs:115 revalidate 전용 API(시크릿 토큰 인증)를 만들고 CLI가 게시 후 호출하도록 합니다.
낮음 목록 페이지마다 전체 글을 select("*")로 가져오므로 본문까지 전송됩니다. 글이 많아지면 느려집니다. lib/posts.ts:107-110 목록용 조회는 필요한 컬럼만 선택하고, 읽기 시간은 저장 시점에 계산해 컬럼으로 둡니다.
낮음 updated_at이 없어 수정 시각을 SEO에 반영하지 못합니다. app/blog/[slug]/page.tsx:76 컬럼을 추가하고 JSON-LD와 sitemap에 반영합니다(로드맵에 이미 있는 항목).
낮음 에러와 성능 지표를 관측할 수단이 없습니다. 프로젝트 전체 instrumentation.ts에 OpenTelemetry를 설정해 Grafana Cloud로 전송합니다.
정리 AdminEditor.tsx가 737줄로 너무 큽니다. components/AdminEditor.tsx 폼, 미리보기, 글 목록, AI 패널로 컴포넌트를 분리합니다.
Spring 전환과의 연결 지점

위 구조에서 화면은 데이터를 lib/posts.ts와 /api/* 두 통로로만 받습니다. 따라서 docs/SPRING-MIGRATION-PLAN.md의 계획대로 Spring API 서버를 만들면, Next.js 쪽에서는 이 두 통로의 호출 대상만 바꾸면 됩니다. 그 시점에 Spring 서버를 Docker 이미지로 만들고 k3s에 배포하면서 Redis와 Prometheus·Grafana를 함께 붙이는 방식으로 인프라를 고도화할 수 있습니다.
